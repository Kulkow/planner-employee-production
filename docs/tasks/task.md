# Задание планировщика

`PlanningJob` — отдельный агрегат контекста планирования. Производственное
задание `ProductionTask` задаёт изделие, количество и технологический процесс;
задание планировщика описывает один запуск расчёта для него.

Поля:

- `id` — уникальный идентификатор запуска;
- `task` — неизменяемые исходные данные: изделие, количество, техпроцесс;
- `planning_day` — дата производственного плана;
- `created_at` — время создания;
- `started_at`, `finished_at` — начало и конец генерации (UTC);
- `duration_sec` — длительность генерации в секундах, отдельно от срока заказа;
- `status` — ожидает запуска, выполняется, завершено, ошибка;
- `result` — полный `ProductionPlan`, включая статус решателя и операции;
- `error` — причина ошибки расчёта.

Переходы: `pending → running → completed | failed`. Завершённое задание
не запускается повторно: новый расчёт создаёт новый идентификатор.
Результат должен соответствовать изделию и количеству задания.

`SubmitPlanningJob` создаёт задание и атомарно сохраняет его вместе с полным
снимком `PlanningRequest` и записью очереди. `PlanningJobService.execute`
запускает уже созданное задание в worker, сохраняет начало, результат или ошибку.
Порты репозитория и очереди определены в application; адаптер
`RedisPlanningJobs` реализует их через JSON, Redis Streams и Pub/Sub.

Сервисы Compose:

- `web` — FastAPI/Uvicorn, HTTP и SSE;
- `worker` — отдельный процесс CP-SAT, потребитель очереди;
- `redis` — очередь, задания, снимки входных данных, Pub/Sub; AOF и том `redis-data`.

Постановка атомарна: HTTP 202 возвращается после записи данных и очереди в
Redis. Worker подтверждает сообщение только после сохранения конечного
состояния. При прерывании обработки неподтверждённая доставка возвращается
другому worker после 5 минут. Если задание уже было `running`, оно завершается
ошибкой о прерывании; если ещё `pending`, выполняется. Задание с конечным
статусом повторно не рассчитывается. Порог восстановления превышает текущий
лимит сравнения четырёх бригад (по 5 секунд поиска допустимости + 20 секунд
оптимизации на каждую, до 100 секунд без учёта построения модели).
При увеличении лимита решателя нужно пересмотреть порог или добавить продление
аренды. Не реализованы автоматический повтор расчёта и очистка истории.

API:

- `POST /api/jobs` — JSON `{"count": 1, "planning_day": "2026-10-05"}`;
  HTTP 202, `job`, `eventsUrl`, `resultUrl`;
- `GET /api/jobs` — метаданные 100 последних заданий;
- `GET /api/jobs/{id}` — состояние в `job`, техпроцесс, ресурсы и результат;
- `GET /api/jobs/{id}/events` — `text/event-stream`, именованные события `job`
  с тем же JSON, что и отдельный запрос состояния; после конечного статуса
  поток закрывается, клиент должен закрыть `EventSource`.

Синхронный `GET /api/plan` заменён на создание задания через POST.
Ошибка расчёта — состояние `failed` с причиной в `job.error`, а не HTTP 500.
Недоступность Redis в обычных HTTP-запросах возвращает 503.

SSE сначала подписывается на канал задания и получает подтверждение подписки,
затем читает сохранённое состояние. Это закрывает гонку с быстрым завершением
worker. Последующие изменения приходят через Pub/Sub, включая завершение каждого
сценария при неизменном статусе задания `running`. Каждые 15 секунд
отправляется heartbeat и повторно проверяется сохранённое состояние.
При переподключении клиент получает актуальное состояние, включая завершённый
результат. Промежуточные состояния могут объединяться: Pub/Sub не является
журналом событий. `Last-Event-ID` и воспроизведение каждого перехода не
реализованы. При обрыве связи с Redis поток отправляет `unavailable` и
закрывается, позволяя браузеру переподключиться.

Техпроцесс доступен в `techProcess` даже для ожидающих и неуспешных заданий.
Операции плана появляются после успешного завершения. Времена расчёта и
срок выполнения заказа — разные величины.

При `compare_departments=true` (по умолчанию в API) worker параллельно
вызывает решатель для каждого department в ограниченном пуле процессов с изолированным набором ресурсов.
`departmentComparison` содержит все сценарии: `departmentId`, `department`,
`status`, `solverStatus`, `error`, `operations` (весь заказ), `start`, `end`,
`workSec` (занятость), `elapsedSec` (время от общей точки начала),
`calculationSec` и `selected` (раньше завершает среди найденных).
`planningOrigin` — общая точка отсчёта; `completedDepartments` — число
уже рассчитанных бригад. Гант использует реальные времена операций этих
сценариев. Промежуточные результаты доступны через GET и SSE.

`horizon_days` — 1–60 календарных дней, по умолчанию 14 в API. Рабочие интервалы
берутся из графиков сотрудников, ночи и выходные исключаются. Операция не
разрывается между сменами. `compare_departments=false` сохраняет обычный
сценарий общего распределения операций между departments. Старые снимки без
этого поля читаются в обычном режиме, без подмены их результатов сравнением.

`departmentOptions` в операциях оставлено для совместимости старых результатов;
локальные оценки больше не используются как сравнение полного заказа.

В каждом элементе `departmentComparison` поле `employees` содержит весь состав
соответствующего department из снимка задания, включая незадействованных
сотрудников. Для каждого сотрудника передаются `id`, `name` и `efficiencies`
по типам оборудования (`equipmentTypeId`, `equipment`, `percent`). Состав и
эффективность отображаются под бригадой до и после завершения расчёта.

`employees[].workloads` содержит дневную загрузку сотрудника с полями
`employeeId`, `date`, `plannedSeconds`, `allocatedSeconds`, `availableSeconds`.
Она берётся из снимка `PlanningRequest.employee_workloads` и отображается
рядом с эффективностью в сравнении бригад. Старые снимки без загрузки
остаются совместимыми и рассчитываются по полной смене.

## Архив PostgreSQL и статистика

Worker сохраняет конечное задание (`completed` или `failed`) вместе с полным
снимком запроса в `planning_history` (JSONB). Отдельные колонки содержат статус,
времена, число операций/сценариев, срок и рабочее время выбранного плана,
а также измерения производительности. Запись идемпотентна по UUID задания.
DDL находится в `planner/infrastructure/sql/001_planning_history.sql`;
применяется при старте web и worker под транзакционной advisory-блокировкой.

Сообщение Redis подтверждается после успешного сохранения PostgreSQL.
При сбое БД конечный результат остаётся в Redis, сообщение — неподтверждённым.
После повторного получения доставки worker архивирует готовый результат
без повторного расчёта. Общей транзакции между Redis и PostgreSQL нет.
Текущее восстановление неподтверждённых доставок — после пяти минут.

`GET /api/jobs/{id}` читает архив, если задания уже нет в Redis или Redis
недоступен. `GET /api/jobs` по-прежнему показывает список из Redis.
Полная долговременная история доступна через `GET /api/statistics`:
`limit` 1–100 (по умолчанию 25), `offset`, необязательный `status`
(`completed` или `failed`). Ответ содержит `items`, агрегаты `summary`,
параметры страницы. HTML-страница — `/statistics`. Ссылка `/?job={id}`
открывает сохранённый план без создания нового расчёта.

`PlanningMetrics` содержит монотонную длительность расчёта, RSS в начале,
наблюдаемый пик RSS и интервал выборки. RSS worker и его дочерних процессов суммируется
каждые 50 мс и включает нативную память OR-Tools. Общие страницы памяти могут
учитываться несколько раз; это не изолированная память
одного задания. Пик может пропустить короткие всплески между выборками.
На странице показаны абсолютный пик и его прирост от начала данного запуска;
не используется накопительный максимум за всю жизнь worker.

Срок производственного плана и длительность его вычисления показаны раздельно.
У старых заданий без метрик длительность берётся из дат начала/окончания,
память остаётся NULL и отображается как «нет данных». Существующую историю
Redis можно перенести идемпотентной командой `python -m planner.migrate_history`.
PostgreSQL настраивается через `DATABASE_URL`. Без этой переменной локальный
режим Redis остаётся доступным, статистика возвращает 503 с объяснением.

## Параллельные расчёты departments

В Redis остаётся одно сообщение на сравнение: родительский worker запускает
отдельный процесс на каждый department через `ProcessPoolExecutor` с `spawn`.
Конкурентность ограничена `DEPARTMENT_PROCESSES` (1–16, по умолчанию 4).
Каждый процесс создаёт свой решатель; соединения Redis/PostgreSQL между
процессами не передаются. Консольный сценарий и прямое использование
`PlanningJobService` без DepartmentRunner сохраняют синхронное поведение.

Только родитель записывает общий `PlanningJob`, публикует SSE и архивирует
конечный результат. Завершение одной бригады не ждёт предыдущих в списке;
ошибка дочернего расчёта записывается как ошибка соответствующего сценария.
`runningDepartmentIds` содержит переданные пулу, но ещё не завершённые
departments (включая ожидающие слот при меньшем лимите).

Поле метрик `memory_scope=process_tree` означает наблюдаемый пик суммарного
RSS родительского worker и его дочерних процессов, а `process` — старый замер
одного worker. Миграция `002_memory_scope.sql` сохраняет различие в PostgreSQL.
Длительность расчёта — общее прошедшее время, а не сумма времени бригад.
