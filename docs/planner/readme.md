# Планировщик производства

Стек: Python 3.12, Google OR-Tools CP-SAT.

## Бизнес-правила примера

- этапы техпроцесса выполняются последовательно;
- группы одного этапа могут выполняться параллельно;
- операции одной группы выполняются по порядку;
- операция назначается сотруднику с требуемым типом оборудования;
- фактическое время операции рассчитывается как
  `ceil(norm_sec * 100 / efficiency_percent)`;
- сотрудник не может выполнять две операции одновременно;
- бригада — это `Department`; каждая операция назначается ровно одному
  сотруднику и тем самым ровно одной бригаде;
- одна бригада выполняет не более одной операции одновременно, даже если
  доступны разные сотрудники; разные бригады могут работать параллельно;
- все операции должны попасть в смену 5/2 с 08:30 до 16:30.

Генератор создаёт четыре бригады (`Department`) по десять сотрудников.
В каждой есть специалисты всех четырёх типов оборудования: решатель выбирает
подходящего исполнителя и бригаду с учётом квалификации и общей занятости.
Эффективность
каждого сотрудника — от 60% до 90%. Создаётся один техпроцесс из шести этапов. В каждом
этапе создаётся от двух до четырёх групп, в каждой группе — от двух до пяти
операций с нормативным временем от 60 до 1500 секунд. Генератор детерминирован
seed-значением. Горизонт ограничен 1–60 календарными днями (в вебе по умолчанию
14). Следующие операции переносятся на доступные рабочие дни; одна операция
не прерывается ночью и должна целиком помещаться в смену.

Перед поиском проверяется нижняя оценка длительности: для каждой группы
суммируются минимальные длительности операций у доступных исполнителей,
затем складываются максимумы групп по этапам. Если даже эта оценка превышает
доступный интервал горизонта, расчёт завершается с понятным сообщением.
Проверка не гарантирует существование плана, если нижняя оценка укладывается
в горизонт: ограничения занятости всё ещё проверяет CP-SAT.

`UNKNOWN` означает, что за отведённое время решатель не определил результат.
Он не равнозначен `INFEASIBLE` (доказано отсутствие допустимого плана).

## Запуск

```bash
docker compose up --build planner
```

Запуск тестов:

```bash
docker compose --profile test run --rm tests
```


## Сравнение бригад

Для каждой бригады (`Department`) весь заказ рассчитывается отдельно, только
с её сотрудниками, квалификациями, эффективностью и рабочими графиками.
Расчёты выполняются параллельно в независимых процессах. Ограничение
`DEPARTMENT_PROCESSES` (по умолчанию 4) действует на один worker; остальные
сценарии ожидают свободного процесса. Результаты собираются по мере готовности. У всех сценариев одинаковые
изделие, количество, техпроцесс, дата начала, горизонт и лимит решателя.

Гант показывает каждый полный сценарий отдельной строкой на общей шкале
времени. Это сравнение альтернатив: словно каждое подразделение независимо
выполняло одинаковый заказ параллельно. Результаты не смешиваются между
бригадами. Сравниваются реальные даты окончания, включая перерывы и выходные,
а не сумма минимальных длительностей отдельных операций.

После каждого сценария сохраняется промежуточный результат и отправляется
SSE. В сравнении остаются ошибки бригад, которым не хватает квалификации,
смен или времени расчёта. Если есть успешные сценарии, итоговый `job.result`
содержит план с самой ранней датой завершения среди найденных. `FEASIBLE`
не означает доказанную оптимальность этого плана. Если все сценарии завершились
ошибками, задание получает `failed` и сохраняет причины для каждой бригады.

Разные запуски остаются независимыми сценариями; общего календаря бронирования
ресурсов между заданиями нет.

При расчёте одного department предварительно строится допустимый
последовательный стартовый план: операции идут по этапам и группам,
сотрудник выбирается по ближайшему возможному окончанию с учётом смен,
выходных и оставшегося дневного бюджета. План передаётся решателю как
подсказка. Если обе фазы поиска возвращают `UNKNOWN` из-за лимита времени,
этот найденный допустимый план сохраняется со статусом `FEASIBLE`.
Это не доказательство оптимальности; если стартовый план построить не удалось,
решатель продолжает обычный поиск, без подмены отсутствующего решения.
