# Правила работы с проектом

## Назначение

Производственный планировщик на Python 3.12 и Google OR-Tools CP-SAT.
Он распределяет операции по сотрудникам с учётом квалификации,
эффективности, рабочего времени и порядка этапов. Бригада — это `Department`:
одна операция назначается одной бригаде, и в одном плане бригада не может
выполнять две операции одновременно. Веб-интерфейс показывает
план на диаграмме Ганта. Общайтесь с пользователем на русском языке.

## Архитектура и DDD

- `planner/domain/` — сущности, агрегаты и бизнес-правила. Не добавляйте сюда
  зависимости от OR-Tools, HTTP, баз данных или application/infrastructure.
- `planner/application/` — сценарии использования и порты (`Protocol`).
  Координируйте доменные объекты и обращайтесь к инфраструктуре через порты.
- `planner/infrastructure/` — CP-SAT, генератор тестовых данных, реализации
  репозиториев и другие внешние адаптеры.
- `planner/web.py` — FastAPI, SSE и встроенная HTML/CSS/JavaScript-страница;
  `planner/presentation.py` — JSON-представление; `planner/worker.py` —
  обработчик очереди; `planner/main.py` — консольная точка входа.
- `tests/` — тесты `unittest`; `docs/` — описание предметной области.

Сохраняйте существующий стиль: типизация, dataclass и неизменяемые доменные
значения там, где это подходит. Бизнес-инварианты проверяйте в домене,
сценарии запуска размещайте в application, сериализацию — на границе HTTP.
Не переносите правила планирования в интерфейс.

## Основные понятия

- `ProductionTask` — изделие (`product_card_id`), количество и техпроцесс.
- `PlanningRequest` — входные данные расчёта, включая сотрудников,
  подразделения, эффективность, графики и дату планирования.
- `EmployeeWorkload` — фонд, уже занятое и доступное время сотрудника на дату.
  Дневная сумма новых назначений не превышает доступный остаток; это бюджет,
  а не точные интервалы существующей занятости.
- `ProductionPlan` — результат решателя и запланированные операции;
  `PlanningJob.department_results` — полные независимые расчёты всего заказа
  для каждого department, включая ошибки отдельных сценариев.
- `PlanningJob` — отдельный запуск генерации с идентификатором, исходным
  производственным заданием, датой, временем создания/начала/окончания,
  результатом или ошибкой.

Переходы задания: `pending → running → completed | failed`. Повторный расчёт
создаёт новое задание. Статус задания и статус решателя имеют разные значения.
Длительность генерации не равна сроку выполнения производственного заказа.
Время жизненного цикла задания храните с часовым поясом UTC.

Активные веб-задания и снимки входных данных хранятся в Redis (JSON).
Конечные задания и полные снимки архивируются в PostgreSQL до подтверждения
доставки. Порт `PlanningJobArchive` расположен в application, адаптер —
`infrastructure/postgres_jobs.py`, DDL — `infrastructure/sql/`. Страница
`/statistics` и API `/api/statistics` читают долговременную историю из PostgreSQL.
Память — наблюдаемый суммарный RSS worker и дочерних процессов за текущий
расчёт, с выборкой 50 мс, включая OR-Tools; общие страницы могут учитываться
несколько раз. Старые замеры одного процесса имеют `memory_scope=process`; не выдавайте её за изолированную память задания. Для исторических
записей без замеров оставляйте NULL. Очередь использует
Redis Streams и consumer group с подтверждением обработки; отдельный worker
выполняет расчёт. Состояния сохраняются и публикуются через Redis Pub/Sub.
SSE подписывается до чтения текущего состояния, отправляет heartbeat и
восстанавливает состояние из Redis при новом подключении. Не запускайте
CPU-затратный решатель в обработчике FastAPI. Консольный сценарий остаётся
синхронным. Redis в Compose использует AOF и именованный том.

## Интерфейс и API

Пользовательские подписи и сообщения пишите понятным русским языком.
Технические статусы переводите в представлении: например, `FEASIBLE` —
«План найден», `OPTIMAL` — «Найден оптимальный план». Сохраняйте машинные
значения статусов в доменных результатах и API.

`POST /api/jobs` принимает `count`, `planning_day`, `horizon_days` (1–60,
по умолчанию 14), `compare_departments` (по умолчанию true), возвращает HTTP 202,
задание и ссылки на результат/SSE. `GET /api/jobs` возвращает до 100 последних
заданий. `GET /api/jobs/{id}` возвращает состояние и результат;
`GET /api/jobs/{id}/events` передаёт SSE-события `job` через Redis Pub/Sub.
В режиме сравнения worker считает весь заказ отдельно для каждого department
в пуле независимых процессов (`spawn`), по умолчанию до четырёх параллельно.
`DEPARTMENT_PROCESSES` задаёт лимит 1–16 на worker. Ресурсы фильтруются в
application; в дочерние процессы передаются только снимки без клиентов БД/Redis.
Общий агрегат и архив записывает один родительский процесс, в порядке готовности
результатов. Прямой сценарий без переданного DepartmentRunner остаётся синхронным
для локального использования и тестов. Сценарии
используют одну дату и горизонт; Гант показывает их параллельно на общей шкале.
Сравнивайте фактическое окончание всего задания, а не минимум одной операции.
Ошибки отдельных бригад сохраняйте; лучший найденный план — результат задания.
Операция целиком помещается в одну рабочую смену; допускается перенос следующей
операции на последующие рабочие дни, с исключением ночей и выходных.
Старый синхронный `GET /api/plan` удалён.
При изменении контракта обновляйте потребителя в интерфейсе и документацию.

## Запуск и проверки

Предпочтительное окружение — Docker Compose:

```sh
docker compose up --build web
docker compose run --rm planner
docker compose --profile test run --build --rm tests
docker compose config --quiet
```

Веб-интерфейс: `http://localhost:8096`.
Локально при установленных зависимостях из `requirements.txt`:

```sh
# Задайте REDIS_URL; запустите Redis и отдельный python3 -m planner.worker.
python3 -m planner.web
python3 -m unittest discover -s tests -v
```

Для отдельной области используйте шаблон тестов, например:

```sh
python3 -m unittest discover -s tests -p 'test_planning_jobs.py' -v
```

Проверяйте изменения бизнес-логики тестами: инварианты, переходы состояний,
успешные сценарии и ошибки. В интеграционных тестах проверяйте ограничения
плана, а не конкретное назначение сотрудников: допустимые решения могут
различаться. Для простых правок текста достаточно проверки diff.
Перед завершением выполните `git diff --check`.
Если проверка недоступна из-за окружения, сообщите об этом явно; не выдавайте
непроверенный результат за успешный прогон.

## Работа с изменениями

Перед редактированием проверьте `git status` и прочитайте затрагиваемый код.
Сохраняйте чужие незакоммиченные изменения. Делайте изменения в рамках
задачи, не добавляйте зависимости без необходимости. Не выводите содержимое
`.env`, ключи и другие секреты. Обновляйте документацию при изменении
предметной модели, API или способа запуска.
